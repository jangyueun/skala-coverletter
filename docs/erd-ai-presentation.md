# ERD 및 AI 기능 발표 정리

## 1. 발표 방향

전체 테이블을 모두 설명하기보다, 서비스의 핵심 흐름을 대표하는 테이블만 설명한다.

주요 테이블은 다음 4개다.

- `experiences`: 사용자 경험 데이터
- `job_postings`: 채용공고 데이터
- `job_matches`: 경험과 공고의 매칭 결과
- `ai_tasks`: AI 작업 상태와 결과 관리

`users`는 모든 데이터의 소유자를 나타내는 기본 테이블이므로, 별도 설명보다는 사용자 기준으로 경험과 매칭 결과가 관리된다고 짧게 언급한다.

## 2. 서비스 핵심 흐름

```text
사용자 경험 등록
        ↓
AI가 경험을 STAR 구조로 정리
        ↓
AI가 채용공고에서 요구 역량 추출
        ↓
경험 역량과 공고 요구 역량 비교
        ↓
job_matches에 매칭 결과 저장
        ↓
자기소개서 문항에 맞춰 AI 초안 생성
```

발표 설명:

> 사용자의 경험과 채용공고를 AI가 동일한 역량 기준으로 구조화합니다. 이후 두 데이터를 비교해 매칭 결과를 제공하고, 매칭된 경험을 활용해 자기소개서 초안을 생성합니다.

## 3. AI 주요 기능

### 3-1. 채용공고 요구 역량 추출

AI가 공고 원문을 분석해 표준 역량, 역량 중요도, 공고 원문의 근거 문장을 추출한다.

```json
{
  "competencyId": 3,
  "weight": 0.9,
  "evidence": "REST API 설계 및 운영 경험이 필요합니다."
}
```

설계 기준:

- AI가 임의의 역량을 새로 만들지 않고 `competencies` 사전 안에서 선택한다.
- 공고 원문의 근거 문장(`evidence_line`)을 함께 저장한다.
- 역량의 중요도를 `weight`로 표현한다.
- 이후 매칭은 역량 ID와 `weight`를 기준으로 계산한다.

발표 설명:

> 공고 분석 결과는 표준 역량 ID, 중요도, 근거 문장으로 구조화하여 저장합니다. 이를 통해 단순 키워드가 아니라 어떤 공고 문장에서 해당 역량이 추출되었는지 확인할 수 있습니다.

### 3-2. 링크·파일에서 사용자 경험 추출

GitHub 링크, PDF, Markdown 등의 자료에서 프로젝트 경험을 추출한다.

추출 항목:

- 경험 제목
- 기간
- 경험 분류
- Situation
- Task
- Action
- Result
- 추천 역량
- 기존 경험과의 중복 여부

자료에 없는 내용을 AI가 임의로 생성하지 않도록, 정보가 부족한 경우에는 추가 질문을 반환한다.

발표 설명:

> AI가 경험을 완성해서 만들어내는 것이 아니라, 자료에서 확인 가능한 내용을 추출하고 부족한 정보는 사용자에게 질문하는 방식입니다.

### 3-3. 경험 데이터 구조화

경험은 하나의 자유 서술문으로 저장하지 않고 STAR 구조로 나눈다.

```text
experiences
 ├─ situation
 ├─ task
 ├─ action
 └─ result
```

경험과 역량은 `experience_competencies` 중간 테이블로 연결한다.

이 구조를 통해 같은 경험 데이터를 다음 기능에서 재사용할 수 있다.

- 역량별 경험 검색
- 채용공고와의 매칭
- 자기소개서 초안 생성

발표 설명:

> 경험 본문은 STAR 필드로 구조화하고, 역량은 별도 사전과 연결해 이후 매칭과 자기소개서 생성에서 재사용할 수 있도록 설계했습니다.

### 3-4. 자기소개서 초안 생성

AI는 다음 정보를 바탕으로 초안을 작성한다.

- 자기소개서 문항
- 글자 수 제한
- 회사와 직무 정보
- 채용공고의 요구 역량
- 사용자가 선택한 경험의 STAR 내용

작성 기준:

- 문항의 요구사항을 먼저 분석한다.
- 관련성이 높은 경험을 선택한다.
- STAR 흐름으로 구체화한다.
- 공고의 요구 역량과 경험을 연결한다.
- 경험에 없는 사실은 생성하지 않는다.
- 글자 수 제한을 준수한다.
- 사용자가 수정할 수 있는 초안으로 제공한다.

발표 설명:

> 자기소개서는 단순히 경험을 요약하는 것이 아니라, 문항과 직무 요구사항에 맞춰 선택한 경험을 재구성해 작성합니다.

## 4. 역량 중요도(`weight`) 산출 기준

### 현재 구현 상태

현재 Mock AI에서는 모든 역량의 중요도를 임시로 `0.9`로 고정하고 있다.

발표 설명:

> 현재는 Mock 단계이므로 중요도를 임시로 고정했으며, 실제 AI 연동 시 공고의 요구 강도와 직무 연관성을 기준으로 산출할 예정입니다.

### 실제 적용 예정 기준

| 기준 | 예시 표현 | 중요도 |
|---|---|---:|
| 필수 조건 | 필수, 반드시, 요구 역량 | 0.9 ~ 1.0 |
| 핵심 업무 | 담당 업무, 주요 역할과 직접 연결 | 0.8 ~ 0.9 |
| 반복 언급 | 공고에 여러 번 등장 | 가산 |
| 우대 조건 | 우대, 선호, 있으면 좋은 | 0.6 ~ 0.7 |
| 부가 기술 | 있으면 도움이 되는 기술 | 0.5 내외 |

중요도는 숫자만 저장하지 않고, 판단 근거가 된 공고 문장도 함께 저장한다.

```json
{
  "competencyId": 3,
  "weight": 0.9,
  "evidence": "REST API 설계 및 운영 경험이 필요합니다.",
  "reason": "핵심 업무와 직접 연결된 필수 역량"
}
```

발표 설명:

> `weight`는 AI가 임의로 부여한 점수가 아니라, 공고의 필수 여부, 업무 연관성, 반복 언급, 우대 조건 등을 반영한 값입니다.

## 5. 매칭 결과

`job_matches`는 사용자의 경험과 채용공고를 비교한 최종 결과를 저장하는 핵심 테이블이다.

저장 정보:

- 전체 매칭 점수
- 매칭 판정
- 충족한 역량 수
- 부족한 역량
- 각 역량을 뒷받침하는 경험
- 매칭 결과의 계산 근거

매칭 점수는 공고 역량의 중요도를 반영해 계산한다.

```text
전체 점수
= Σ(역량 중요도 × 경험 보유 점수)
  ÷ Σ(역량 중요도)
```

발표 설명:

> 모든 역량을 동일하게 보는 것이 아니라, 공고에서 더 중요한 역량에 더 큰 가중치를 부여해 매칭 점수를 계산합니다.

## 6. `ai_tasks` 테이블의 역할

AI 기능마다 별도의 작업 테이블을 만들지 않고, `ai_tasks`에서 통합 관리한다.

관리 대상:

- 공고 분석
- 경험 추출
- 매칭 계산
- 자기소개서 초안 생성

관리 정보:

- 작업 유형
- 작업 상태
- 요청 데이터
- AI 응답 결과
- 모델명
- 프롬프트 버전
- 실패 사유
- 재시도 이력

작업 상태:

```text
PENDING → RUNNING → COMPLETED
                     └→ FAILED
```

발표 설명:

> `ai_tasks`는 AI 결과 자체를 저장하는 테이블이라기보다, 비동기 AI 작업의 상태·요청·결과·실패 이력을 통합 관리하는 테이블입니다.

## 7. 현재 구현 범위

AI 구현이 완성되지 않았다면 다음처럼 구분해서 설명한다.

> 현재는 AI 입출력 형식과 작업 관리 구조를 구현하고 Mock AI로 전체 흐름을 검증했습니다. 실제 LLM 모델 연동은 확장 단계에 있으며, 모델이 연결되더라도 동일한 데이터 구조와 작업 관리 방식을 사용할 수 있도록 설계했습니다.

| 구분 | 현재 상태 |
|---|---|
| AI 기능 흐름 설계 | 구현 |
| AI 요청·응답 형식 | 구현 |
| `ai_tasks` 작업 관리 구조 | 구현 |
| 경험·공고 데이터 구조화 | Mock 기반 검증 |
| 실제 LLM 호출 | 연동 예정 |
| AI 결과 품질 검증 | 실제 모델 연동 후 진행 |

## 8. 최종 발표 멘트

> 저희 서비스의 핵심은 사용자의 경험과 채용공고를 AI가 같은 역량 기준으로 구조화하는 것입니다. 공고에서는 요구 역량과 중요도, 근거 문장을 추출하고, 사용자의 링크나 파일에서는 경험을 STAR 구조로 정리합니다. 이후 두 데이터를 비교해 `job_matches`에 매칭 결과를 저장하고, 선택한 경험을 바탕으로 자기소개서 초안을 생성합니다. 현재는 Mock AI를 통해 전체 데이터 흐름과 작업 관리 구조를 검증했으며, 실제 LLM 연동을 확장할 수 있도록 `ai_tasks` 중심으로 설계했습니다.
