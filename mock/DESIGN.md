# 미니프로젝트 · 경험 · 역량 매핑 트래커

SKALA 8주차 **AI 웹 서비스 설계 Mini-project**(3일 · 5인) 후보 주제 B의 작업 폴더.

```
mini-project/
├── README.md
├── mockup/
│   └── index.html      ← 클릭 가능한 목업 (더블클릭해서 브라우저로 열면 됨)
└── docs/               ← ERD DDL · OpenAPI 명세가 들어갈 자리
```

## 한 줄 정의

> 지원 가능한 공고를 **나와의 매칭도**로 줄 세우고, 어떤 경험이 어떤 요구 역량을 덮는지 짚어 주며,
> 공고별 자소서를 버전으로 관리하는 취업 준비 도구.

## 서비스의 근거

7주차 취업특강(§21)에 이렇게 나온다.

> **"해당 직무와 연관된 핵심 역량 단어가 자소서에 있는지 없는지를 AI로 돌린다.**
> **넣어야 할 키워드는 ① 지원 직무의 핵심 역량 키워드 ② 그 회사 인재상 키워드다."**
>
> **"거의 대부분의 자소서를 보면 그런 키워드를 넣을 생각을 안 하시는 것 같아요.**
> **제가 본 적이 거의 없는 것 같습니다."**

**기업이 제출 후에 돌리는 그 대조를, 제출 전에 미리 돌려 보는 것**이 이 서비스다.

## ⚠️ 포지셔닝 — 발표 첫 문장에서 못 박을 것

이 서비스는 **"AI 자소서 대필기"가 아니다.** 1차 가치는 경험 자산의 구조화와 재사용이고,
AI는 그 위에 얹히는 가속기다. 대필기로 포지셔닝하면 AI를 뺐을 때 아무것도 안 남고,
*"AI-Ready = AI 없이도 동작하되 자리를 비워 둔 구조"* 라는 과제의 전제가 무너진다.

목업의 **문장 점검 7개 항목이 전부 문자열 규칙**이다. LLM을 빼도 그대로 돈다.

## 목업 사용법

`mockup/index.html` 을 브라우저로 연다. 빌드도 서버도 필요 없다.

화면은 **3개**다. 공고 하나에 대한 모든 것은 그 공고 상세 안에 있다.

| 화면 | 내용 |
|---|---|
| **공고 찾기 (홈)** | 활성 공고 카드 그리드 · 매칭순/마감순 정렬 · 즐겨찾기 필터 |
| **공고 상세** | 카드를 누르면 열린다. 탭 3개 — **공고 내용 / 매칭 / 자소서** |
| 경험 라이브러리 | STAR 경험 목록, 역량 칩 필터, 경험 등록 |

지원 현황을 별도 화면으로 두지 않았다. 자소서 진행은 **공고 카드에 붙어 있는 게 맞다** —
"내가 어디에 지원했나"를 따로 보는 것보다 "이 공고를 어디까지 썼나"가 실제 행동 단위다.

### 제출 여부는 모델에 두지 않는다

`application.status`(지원 예정/작성 중/제출/면접/결과)를 통째로 뺐다.
**우리는 사용자가 실제로 제출했는지 알 수 없다.** ATS 연동이 없으니 자기 신고밖에 안 되고,
자기 신고 값을 시스템이 아는 사실처럼 화면에 찍으면 `strength`·`weight` 와 같은 함정이 된다.

대신 진행 상태를 **관측 가능한 것에서 파생**한다 — `questions` 의 `draft` 유무:

| 상태 | 판정 |
|---|---|
| 지원서 없음 | 이 공고에 `application` 이 없다 |
| 문항 미등록 | `application` 은 있고 `question` 이 0건 |
| 작성 전 | 문항은 있고 `draft` 가 하나도 없다 |
| 작성 중 | 일부만 작성 |
| 작성 완료 | 전부 작성 |

`자소서 N개 공고에 사용` 배지도 같은 원칙이다 — **근거로 걸려 있고 본문이 실제로 작성된**
답변만 세고, 서로 다른 **공고** 수로 센다. 체크만 하고 안 쓴 문항은 세지 않는다.
공고가 직무 단위라 같은 기업의 다른 직무에 썼으면 2건이다 — 기업 단위로 세면 그 구분이 사라진다.

> 이 서비스가 다루는 값은 세 종류다 — **관측**(마감일·글자 수·근거 연결),
> **산출**(매칭 커버리지·갭), **신고**(역량 강도). 셋을 섞어 같은 숫자로 보여주지 않는 게 원칙이다.

### 관련 공고 — 같은 기업 다른 직무 / 다른 기업 같은 직무

공고 상세의 **공고 내용** 탭 하단에 두 묶음을 보여준다. `role` 은 수집 시 분류하는
직무 계열이다 — 기업이 쓰는 직무명이 제각각이라 문자열로는 못 묶는다
("서버 개발"과 "백엔드 엔지니어"는 같은 계열).

요구 역량 목록은 **매칭 탭에만** 둔다. 공고 내용 탭에 같이 두면 겹친다.

### 같은 기업이라도 직무가 다르면 다른 공고다

| 기업 | 직무 | 매칭 | 자소서 |
|---|---|---|---|
| **세움테크** | 백엔드 엔지니어 | 69% (갭 2) | 1/4문항 |
| **세움테크** | 프론트엔드 엔지니어 | **87%** (갭 0) | 미지원 |
| **한빛시스템** | 플랫폼 엔지니어 | 94% (갭 0) | 문항 미등록 |
| **한빛시스템** | SRE | **78%** (갭 1) | 1/2문항 |

카드에 `이 회사 2건` 배지가 붙고, 상세 헤더에서 **같은 기업의 다른 직무로 바로 이동**할 수 있다
(`프론트엔드 엔지니어 · 87%`). 같은 회사인데 매칭이 18%p 벌어지는 게 한눈에 보인다 —
`posting` 이 기업이 아니라 **직무 단위 엔티티**라는 걸 데이터로 보여주는 장치다.

### 공고 상세의 탭 3개

| 탭 | 내용 |
|---|---|
| **공고 내용** | 원문을 `담당 업무 / 자격 요건 / 우대 사항 / 인재상` 으로 파싱해 표시 + 추출된 요구 역량 |
| **매칭** | **평가 요약 카드** + 커버리지, 갭, 역량 클릭 시 근거 경험 |
| **자소서** | 문항 목록 · 문장 점검 7종 · 80% 분량 눈금 · 근거 경험 · 초안 생성 · 문항 추가 |

**자소서 에디터를 따로 두지 않은 이유** — 자소서는 언제나 특정 공고의 것이다.
공고를 벗어난 자소서 에디터는 "어느 회사 자소서를 쓰는 중인지"를 사용자가 기억하게 만든다.
실제로 이전 구조에서는 문장 점검이 편집 중인 지원서가 아니라 전역 활성 공고를 기준으로 도는 버그가 있었고,
IA를 공고 중심으로 바꾸자 그 버그가 구조적으로 불가능해졌다.

### 평가 요약 카드 — 숫자 말고 판정

매칭 탭 최상단에 있다. 요구 역량과 내 경험을 넣고 **판정 · 요약 · 다음 할 일**을 받는다.

```
조건부 지원   기술 역량은 채웠지만 인재상 키워드가 비어 있습니다

요구 역량 10개 중 8개를 덮어 매칭 73%입니다. 백엔드 서버 개발은 “MSA 주문·결제 서비스 구축”과
“주식 거래 REST API 개발”이 뒷받침합니다. 반면 AI 도구 활용(가중치 0.7), 도메인 이해
(가중치 0.7)은 이를 증명할 경험이 없습니다. 마감이 10일 남아, 새 경험을 만들기보다
기존 경험을 이 공고의 언어로 다시 서술하는 편이 현실적입니다.

지금 할 일
1 [낮음] 인재상 키워드입니다. MSA 프로젝트에서 AI 도구를 어떻게 썼는지 한 문단 보강하세요.
2 [중간] 물류·정산 도메인 경험이 없습니다. 도메인 용어를 학습한 뒤 …
3 [낮음] 데이터 설계·처리: “주식 거래 REST API 개발”에 이 역량이 드러나는 수치를 보강하세요.
4 [중간] 자소서 4문항 중 3문항이 비어 있습니다.
```

**이 문장은 하드코딩이 아니다.** `computeMatch` 결과에서 조립하므로 경험을 추가하면 그대로 바뀐다 —
`AI 도구 활용` 을 덮는 경험을 등록하면 요약이 *"도메인 이해가 비어 있습니다"* 로, 매칭이 73% → 80% 로 이동한다.

**평가는 사용자가 돌리지 않는다 — 이벤트로 갱신된다.**
화면에 재평가 버튼이 없다. 경험 라이브러리가 바뀌면 이벤트가 발행되고, 서버가 활성 공고들의 평가를
다시 계산해 `assessment` 에 저장한다. 화면은 저장된 결과를 읽기만 한다.

```
2026-09-02 06:10  BATCH    nightly reassess × 5
2026-09-02 12:51  EVENT    ExperienceCreated { experienceIds: [99] }
2026-09-02 12:51  ENQUEUE  reassess × 5 (활성 공고)
2026-09-02 12:51  RUN      POST /internal/ai/match × 5
2026-09-02 12:51  DONE     upsert assessment × 5
```

카드 상태는 `평가 최신 · 시각` → `재계산 대기` → `재계산 중` → `평가 최신 · 갱신 시각` 으로 움직이고,
계산 중에는 이전 결과가 흐려진 채로 남는다. **AI 응답은 입력이 바뀌면 낡는다는 걸 UI가 인정한다.**

5주차에 배운 **이벤트 발행 → 컨슈머 재계산** 구조가 그대로 대응한다 — 발표에서 MSA·Kafka 학습과
이 프로젝트를 잇는 지점이다.

**어느 탭에 있든 보이게** 상세 헤더에 한 줄 판정 스트립을 뒀다 (`조건부 지원 · 헤드라인 · 평가 보기 →`).

설계 주석 모드를 켜면 **프롬프트에 들어가는 입력 JSON** 이 그대로 보인다 —
`posting / required[] / experiences[] / coverage[]`. 카드가 API 계약 데모를 겸한다.

### 서버가 자소서 문항을 주지 않았을 때

수집한 공고에 자소서 문항이 늘 붙어 있지는 않다. 자소서 탭은 세 상태를 구분한다.

| 상태 | 화면 |
|---|---|
| 지원서 없음 | "이 공고로 지원서 만들기" |
| 지원서는 있으나 **서버가 문항을 주지 않음** | `GET /postings/{id}/questions → 200 { "questions": [] }` 를 보여주고 **문항 직접 추가** 유도 |
| 문항 있음 | 전체 에디터 |

목업에서 한빛시스템·코어링크가 **문항 없음** 상태다. 문항을 직접 추가하면
이후 점검·초안·버전 관리가 다른 공고와 똑같이 동작한다.

### 즐겨찾기

카드 우상단과 상세 헤더에서 담고 뺀다. 홈 상단의 **즐겨찾기만** 토글로 걸러 본다.
실제 구현은 `bookmark` 테이블 (**N:M · user ↔ posting**), 목업에서는 브라우저에 남긴다
(`localStorage` 접근이 막힌 환경에서도 안전하게 동작하도록 감쌌다).

### 등록 기능 4개 — 객체 모델의 모든 생성 경로

| 무엇 | 어디서 | 대응 엔드포인트 |
|---|---|---|
| 경험 | S1 `＋ 경험 등록` | `POST /api/experiences` |
| 경험 수정 | 경험 카드의 `수정` | `PUT /api/experiences/{id}` |
| 지원서 | S5 `＋ 지원 등록` · 홈 `지원서 만들기` | `POST /api/applications` |
| 문항 | 홈 `문항 추가` · S4 `＋ 문항 추가` | `POST /api/applications/{id}/questions` |
| 답변 | 자소서 탭 `저장` | `PUT /api/answers/{id}` |

경험 카드의 `수정` 을 누르면 같은 다이얼로그가 **수정 모드**로 열린다 — STAR·역량·강도가 전부 채워진 채로,
인테이크 탭은 감춰지고(이미 있는 경험을 고치는 중이므로), 저장하면 새로 만들지 않고 그 행을 갱신한다.
수정도 등록과 똑같이 `ExperienceUpdated` 이벤트를 발행해 평가가 다시 계산된다.

경험 등록 다이얼로그는 **역량 사전 20개 안에서만** 태그하게 강제하고, 각 역량에 **약 0.4 / 중 0.7 / 강 0.9**
강도를 매긴다 (`experience_competency.strength`). 결과(R)에 숫자가 없으면 그 자리에서 경고한다.
등록 직후 **매칭이 몇 %p 올랐는지** 토스트로 알려 준다 — 갭을 메우는 행동이 곧바로 보상된다.

### 상단 토글 2개

- **설계 주석** — 각 UI 요소가 어떤 API·테이블에 대응하는지 배지로 표시된다.
  S2·인테이크에서 켜면 `202 Accepted → 폴링 → COMPLETED` 네트워크 로그가 함께 뜬다.
  **발표할 때 이걸 켜고 설명하면 화면 하나로 API 명세와 ERD를 같이 보여줄 수 있다.**
- **다크** — 라이트/다크 전환.

## AI 확장 지점 4개 — 유형이 전부 다르다

| 지점 | 유형 | temp | 위치 |
|---|---|---|---|
| **AX-1** | 추출 | 0.0 | 공고 원문 → 요구 역량 + 가중치 + 근거 인용 |
| **AX-2** | 매칭·랭킹 + 요약 | 0.2 | 내 경험 세트 × 요구 역량 → 커버리지·갭 + **판정·요약·다음 할 일** |
| **AX-3** | 생성 | 0.6 | 문항 + 근거 경험 → 자소서 초안 |
| **AX-4** | **대화형 추출** | 0.2 | 포트폴리오·GitHub 링크 → 경험 후보 + **되묻는 질문** |

### AX-4 가 이 설계의 핵심 논거다

경험을 STAR로 6개 쓰라고 하면 아무도 안 쓴다. 그래서 링크를 넘기면 AI가 읽는다.
그런데 **저장소에서 알 수 있는 것은 S(상황)와 A(행동)뿐이다.**
T(목표)와 R(수치)는 본인 머릿속에만 있다. 그래서 지어내지 않고 **질문으로 되묻는다.**

**질문지가 아니라 에디터다.** 처음에는 3단계 위저드(후보 선택 → 질문 → 확인)로 만들었는데,
질문 칸에 답을 적는 것이 *AI 에게 먹이를 주는* 느낌이었다. 답을 적은 뒤에도 최종 문장을
고칠 수 없었고, 확인 화면에서 틀린 걸 발견하면 뒤로 돌아가야 했다. 2단계로 줄였다.

```
1 / 2  후보 선택   링크 여러 개 → 후보 5건 · 다중 선택 · 이미 등록된 것은 중복 감지로 비활성
2 / 2  편집        좌: 후보 레일(상태 · 수정 여부) | 우: 그 후보의 STAR 에디터 4칸
```

확인 화면이 없는 이유는 **2단계가 곧 최종 문서**이기 때문이다. 직접 입력 폼과 같은
`textarea` 4개를 쓰고, AI 가 쓴 S·A 도 그 자리에서 고칠 수 있다.

**대신 "누가 쓴 문장인가" 를 네 겹으로 표시한다.** 이게 사라지면 이 기능의 존재 이유가 없다.

| 겹 | 방식 |
|---|---|
| 필드 왼쪽 스트라이프 | 회색 3px = AI 원문 · 강조색 = 내가 고침 · 주황 5px = 아직 안 씀 |
| 배지 | `AI · 근거 확인됨` / `AI 문장 → 내가 고침` / `저장소에 없음 · 본인만 아는 것` / `내가 씀` |
| 붙는 보조정보 | AI 칸에는 **근거 인용**, 본인 칸에는 **질문과 “왜 묻는가”** |
| 등록 후 | 경험 카드 배지에 `포폴 인테이크 · 일부 수정` 까지 남는다 |

“고쳤다”를 플래그로 저장하지 않고 **매번 원문과 비교한다.** 고쳤다가 원문 그대로
되돌리면 표시도 저절로 원상복구되고, 편집해 놓고 AI 표식만 남기는 세탁이 불가능하다.

**AI 문장을 통째로 지우면 근거가 따라가지 않는다.** `evidenceRefs` 가 비고, 경험 카드는
`포폴 인테이크 · 본인이 다시 씀` 이 된다. 다시 쓴 문장에 `PR #412 · merged` 를 근거로
달면 근거가 아무 데나 찍히는 도장이 되기 때문이다.

```
T · 무엇을 목표로 삼았나          [저장소에 없음 · 본인만 아는 것]
   이 버그를 고치기로 한 계기는 무엇이었고, 어디까지 고치는 것을 목표로 잡았나요?
   왜 묻는가 — PR 에는 무엇을 고쳤는지는 있지만 왜 이 문제를 골랐는지는 없습니다.
   ┌──────────────────────────────────────────────┐
   └──────────────────────────────────────────────┘
```

3건을 골라 2건만 채우면 **2건만 등록된다.** 등록 버튼은 다이얼로그 하단에 상주하며
`2건 등록` · `아직 비어 있는 1건은 등록되지 않습니다 · 세움테크 매칭 73% → 76%` 로
상태와 효과를 편집 내내 보여준다. 3단계에서 한 번 보던 숫자가 이제 계속 보인다.

**되물은 칸을 채우지 않으면 경험을 만들지 않는다.** 규칙은 그대로다. 다만 근거가
`답변 개수 == 질문 개수` 라는 인덱스 우연이 아니라 **“AI 가 되물은 칸”** 이 됐다.
AX-4 가 언젠가 README 벤치마크에서 R 을 실제로 찾아내 질문에서 빼면 규칙이 저절로 따라간다.

경험 삭제 경로가 없어 등록은 되돌릴 수 없다. 그래서 미완 건을 버리는 확정만
**한 번 멈춘다** — `1건만 등록 · 한 번 더`. 초안을 한 글자라도 고치면 무장이 풀린다.

이건 8주차 PART 4(도구와 에이전트)의 대화형 패턴이고, 다른 세 지점과 성격이 다르다.

### 요구 역량 추출은 사용자가 하지 않는다

AX-1 은 **수집 배치의 일부**다. 크롤러가 공고를 적재하는 시점에 추출까지 끝내 두므로,
사용자가 상세를 열 때 기다릴 일이 없고 파서·프롬프트는 서비스 운영자만 손댄다.
화면에는 추출 버튼이 없고, 설계 주석 모드에서 **읽기 전용 배치 기록**만 보인다.

```
2026-09-01 04:12  crawl  https://careers.seumtech.example/jobs/2026-be
2026-09-01 04:12  POST /internal/ai/extract  { postingId: 9 }
2026-09-01 04:12  200  { required: 9, newCompetencies: 2, latencyMs: 1240 }
2026-09-01 04:12  UPSERT  posting_competency × 9
```

AX-2(평가)도 마찬가지다 — **경험 라이브러리 변경 이벤트**에 반응해 서버가 미리 계산해 둔다.

그래서 **사용자가 트리거하는 AI는 AX-3(초안 생성)과 AX-4(포트폴리오 인테이크) 둘뿐**이고,
`202 + 폴링` 데모는 그 둘에서 그대로 볼 수 있다.

| 확장 지점 | 언제 도는가 | 사용자가 기다리나 |
|---|---|---|
| AX-1 추출 | 공고 수집 배치 | 아니오 |
| AX-2 평가 | **경험 변경 이벤트** · 야간 배치 | 아니오 |
| AX-3 초안 | 사용자가 버튼을 누를 때 | 예 (202 + 폴링) |
| AX-4 인테이크 | 사용자가 링크를 줄 때 | 예 (202 + 폴링) |

### AI API로 실제 구현 가능한가 — 가능하고, 호출은 2번이면 된다

| 단계 | 방식 |
|---|---|
| 후보 여러 개 + 후보별 질문 | **LLM 호출 1번.** 구조화 출력으로 `candidates[]` 를 강제하고, 각 후보 안에 `questions[]` 를 같이 뱉게 한다. Spring AI는 `BeanOutputConverter` / `.entity(...)` 로 JSON 스키마를 강제하고 실패 시 재시도한다 |
| 답변을 STAR로 합치기 | **서버 로직이면 충분.** 답변을 T·R 필드에 그대로 넣는다. 문장을 다듬고 싶을 때만 LLM 호출 1번 추가 |

현실적 제약 세 가지:

1. **컨텍스트** — 저장소 전체를 넣을 수 없다. `README + 파일 트리 + 주요 파일 일부 + 커밋 메시지 요약` 으로 압축해 넣는다. 즉 실제 파이프라인은 `수집 → 압축 → LLM` 이다.
2. **비용·지연** — 후보 5건에 근거 인용까지 뱉으면 출력 토큰이 크다. 그래서 `202` 비동기가 맞다.
3. **할루시네이션** — 프롬프트 규칙만으로는 부족하다. `evidence` 에 **원문 인용을 반드시 넣게** 하고, **서버가 그 인용이 실제 파일에 있는지 문자열 포함으로 검증**한다. 없으면 그 후보를 버린다. 구현이 쉽고 방어력이 크다.

### 첨부파일도 읽을 수 있나

| 소스 | 가능성 |
|---|---|
| GitHub 저장소 | 공식 API로 README·파일 트리·PR 조회. 크롤링이 아니라 API 호출이라 안정적 |
| PDF (발표자료 · 이력서) | 텍스트 추출로 충분히 가능. 목업의 근거 표시에 `DOC · 발표자료.pdf` 가 들어 있는 이유 |
| 마크다운 · 노션 공개 페이지 | 마크다운은 쉽다. 노션은 SPA라 서버 fetch로는 본문이 안 나오는 경우가 많아 커넥터가 정석 |
| 이미지 | OCR 필요. 3일 스코프 밖 |

⚠️ **사용자가 준 링크를 서버가 그대로 fetch 하는 것은 SSRF 위험**이 있다.
허용 도메인 화이트리스트 · 응답 크기 제한 · 타임아웃이 필요하다. 설계 문서에 적을 실제 고려사항이다.

## 공고는 어떻게 들어오는가

개인이 URL을 넣어 크롤링하지 않는다. **백엔드가 기업별 채용 페이지를 주기적으로 수집**하고,
적재할 때 AX-1 추출까지 배치로 끝내 둔다.

| | 개인 URL 크롤링 | 백엔드 수집 (채택) |
|---|---|---|
| 파서 개수 | 지원자가 넣는 임의 URL만큼 | **등록된 기업 수만큼** |
| 실패 시 | 사용자 흐름이 그 자리에서 끊김 | 백그라운드라 사용자는 모름 |
| 캐싱 | 안 됨 | 한 번 파싱하면 전원이 씀 |
| 마감일 | 사용자가 직접 입력 | **자동 갱신** |
| 데모 위험 | 높음 | 없음 |

그래서 홈과 S2는 **이미 파싱이 끝난 활성 공고를 매칭순으로** 보여준다.
목록에 없는 공고는 원문을 직접 붙여넣으면 된다.

> 인기순(지원자 수) 정렬은 넣지 않았다. 공고 사이트가 지원자 수를 공개할 때만 가능한 지표라,
> 없는 데이터를 있는 척할 수 없다.

## 90초 데모 흐름

1. **홈** — 활성 공고가 카드로, 매칭순. 한빛시스템 플랫폼 76% / 세움테크 백엔드 73% / 세움테크 프론트 62%
2. 세움테크 백엔드 `매칭` → **S3** 갭 2개(`AI 도구 활용`, `도메인 이해`). 인재상 키워드가 비어 있다
3. **S1** `＋ 경험 등록` → `포트폴리오에서 가져오기` → 링크 4개 분석 (202 → 폴링)
4. 후보 5건 중 **3건 선택** → 각각의 질문 6개 → **4개만 답한다**
5. 확인 화면에 **완성된 2건만** 미리보기, 미완 1건은 경고 → 등록
6. 토스트 **"경험 2건 등록 · 매칭 70% → 75% (+5%p)"**
7. **S4** 문항 선택 → 문장 점검 **5건** → `초안 생성` → **이상 없음** → `새 버전 저장` (v1)

## 목업 데이터의 출처

기업·공고·지원자는 전부 가상이다. 다만 **평가 기준과 감점 수치는 실제 강의 자료에서 뽑았다.**

| 목업 안의 것 | 출처 |
|---|---|
| 역량 사전 20개 | 2026년 하반기 실제 채용공고 72건의 자격요건·우대사항·인재상 문장 |
| 인재상(VALUE) 범주 | 같은 공고들의 인재상·우대사항 문장 (§21 ③ 직무 키워드 적합도와 대응) |
| 분량 85% · 기업명 오기 75% · 근거 없는 역량 60% · 수치 없는 성과 45% | 취업캠프 자기소개서 작성 가이드 |
| 검토 시간 5분 미만 62% → 두괄식 | `강의정리_260828.md` §22, §26 |
| 기업 AI 검사 3종 (표절 42% / 결격 28% / 직무 키워드 18%) | 취업캠프 자기소개서 작성 가이드 |
| 금지 표현 10종 | `강의정리_260828.md` 부록 D |
| 문항 구조와 평가 의도 | SKALA 서류 전형 문항을 가상 공고에 맞춰 각색 |

### 역량 사전에 VALUE(인재상)를 따로 둔 이유

`자기주도 학습`과 `주도성·오너십`은 뜻이 겹친다. 그래도 나눴다 —
**같은 뜻이라도 그 회사가 쓰는 단어를 그대로 써야 AI 키워드 매칭에 걸리기 때문**이다.
실제 공고에서도 두 갈래로 갈려 나온다: "새로운 기술을 습득하고 업무에 적용하는 것을 즐기는 분"과
"스스로 문제를 발견하고 끝까지 책임지는 분"은 같은 문장에 같이 쓰이지 않는다.

역량마다 `aliases` 를 둬서 문장 안의 동의어도 잡는다 (`클라우드 인프라 운영` ← AWS · 쿠버네티스 · Docker · 리눅스).

## 검증 기록

브라우저에서 직접 실행해 확인했다 (JS 에러 0건, 모바일 375px 6화면 가로 넘침 0).
5개 렌즈(런타임 · 데이터 정합성 · 테마/접근성 · 사실 정확성 · UX)로 적대적 리뷰를 돌려
**39건 제기 → 25건 확정 → 전부 수정**했다. 주요 수정:

| 무엇이 틀렸었나 | 어떻게 고쳤나 |
|---|---|
| 문장 점검이 편집 중인 지원서가 아니라 활성 공고 기준으로 돌았다 | 문항 → 지원서 → 공고로 거슬러 올라가 판정 |
| 마감일·매칭·문항 진행이 화면마다 달랐다 | 같은 사실을 두 곳에 저장하지 않고 전부 파생 |
| 회사명 오기 목록이 고정 배열이라 공고를 바꾸면 어긋났다 | `내가 아는 모든 기업 − 지금 쓰는 기업` 으로 파생 |
| **§21 ②를 인재상 키워드 근거로 잘못 인용** | 원문은 §21 **③ 직무 키워드 적합도** 안의 두 번째 항목 |
| 금지 표현 2종이 원문에 없는 창작이었다 | 채용 트렌드 자료의 실제 BAD 예시로 교체 |
| "즉시 탈락" 표현 | 원문대로 "채점자 0점" |
| 설계 주석 모드 배지가 다크에서 대비 미달 | 하드코딩 `#fff` 제거, 토큰으로 |
| 표 행을 키보드로 조작할 수 없었다 | `tabindex` + Enter/Space |
