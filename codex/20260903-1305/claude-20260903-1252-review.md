## P0-1. Supabase ERD/API와 현재 Slack 구현이 충돌

최종 ERD/API는 다음을 전제로 한다.

- `users.supabase_user_id UUID`
- `Authorization: Bearer {Supabase Access Token}`
- `GET /api/me`
- 미인증이면 401

현재 백엔드는 다음을 구현하고 있다.

- `users.slack_team_id + slack_user_id`
- Slack OAuth + 서버 세션
- `GET /api/auth/me`
- 미인증이면 `200 + null`

둘은 단순 컬럼명 차이가 아니라 인증 주체, 사용자 식별자, 세션 방식, API 상태 코드가 전부 다른 계약이다.

### 권장 결정

사용자가 요청한 Supabase 방식을 최종안으로 채택한다면 다음을 함께 변경한다.

1. Slack 전용 사용자 엔티티와 로그인 흐름을 Supabase JWT 검증 방식으로 교체한다.
2. 모든 `/api/**` 요청에서 JWT `sub`로 `users.supabase_user_id`를 찾는다.
3. Career DB 사용자 행 생성 방법을 API에 추가한다.

권장 API:

```http
PUT /api/me
Authorization: Bearer {supabaseAccessToken}
```

```json
{
  "name": "정하윤",
  "profileImageUrl": null
}
```

동일한 `sub`가 없으면 INSERT, 있으면 프로필 UPDATE하는 멱등 upsert로 정의한다. 현재 명세의 `GET /api/me`만으로는 Supabase 회원가입 후 Career DB의 `users` 행을 누가 생성하는지 정의되지 않았다.

Slack을 유지한다면 반대로 최종 ERD/API에서 Supabase 관련 내용을 제거하고 현재 Slack 식별자·세션 계약에 맞춰야 한다. 두 방식을 동시에 최종안으로 둘 수 없다.

## P0-2. `job_posting_questions.is_active`와 UNIQUE가 충돌

현재 ERD는 답변이 연결된 옛 문항을 hard delete하지 않고 `is_active=false`로 보존한다. 방향은 맞다.

하지만 동시에 다음 전역 유니크가 존재한다.

```text
UNIQUE(job_posting_id, sequence)
```

예를 들어 공고 1번의 기존 1번 문항을 비활성화한 뒤 새 1번 문항을 INSERT하면, 기존 비활성 행 때문에 UNIQUE 위반이 발생한다.

기존 행의 문구를 UPDATE하면 과거 사용자의 답변이 새 질문에 달린 것처럼 바뀌므로 더 위험하다.

### 필수 수정

DBML에서 다음 유니크를 제거한다.

```dbml
(job_posting_id, sequence) [unique]
```

생성 SQL을 다시 만든 뒤 constraints SQL에 활성 행만 대상으로 하는 부분 유니크 인덱스를 둔다.

```sql
CREATE UNIQUE INDEX uq_job_posting_question_active_sequence
  ON job_posting_questions (job_posting_id, sequence)
  WHERE is_active = true;
```

추가 스모크 테스트:

1. `(posting=1, sequence=1, active=true)` 등록
2. 기존 문항을 `active=false`로 변경
3. 같은 `(posting=1, sequence=1, active=true)` 신규 등록 성공 확인
4. 활성 1번 문항을 한 건 더 등록하면 실패 확인

## P0-3. MATCH 단일 실행 방지가 최신 변경을 버릴 수 있음

`uq_ai_task_match_inflight(user, posting)`은 동시에 MATCH 두 개가 실행되는 것을 막는다. 하지만 다음 시나리오가 생긴다.

1. 경험 A 기준 MATCH가 RUNNING
2. 사용자가 경험 B를 추가
3. B를 반영한 새 MATCH INSERT 시도
4. 부분 유니크 인덱스로 두 번째 요청 차단
5. 기존 작업은 A 기준 결과로 완료
6. B 기준 재계산 요청이 사라짐

DRAFT는 사용자가 409를 보고 다시 누를 수 있지만, 경험 변경으로 자동 발생하는 MATCH에는 사용자가 재시도할 버튼이 없다. 따라서 같은 인덱스를 일괄 적용하면 안 된다.

### MVP 권장안

- `uq_ai_task_draft_inflight`: 유지
- `uq_ai_task_intake_inflight`: 유지
- `uq_ai_task_extraction_inflight`: 유지
- `uq_ai_task_match_inflight`: 제거
- MATCH 결과를 Career DB에 반영하기 직전에 `input_hash`가 현재 경험 상태 해시와 같은지 확인
- 다르면 해당 결과를 폐기하고 최신 입력으로 새 MATCH 생성

또는 MATCH 단일 실행을 유지하려면 충돌 시 `rerun_requested`와 최신 입력 스냅샷을 영속화하고, 현재 작업 완료 직후 반드시 한 번 더 실행하는 coalescing 설계가 필요하다.

추가 스모크/통합 테스트에는 “MATCH 실행 중 경험을 다시 수정했을 때 최종 `job_matches.input_hash`가 최신 경험 해시가 되는가”가 포함돼야 한다.

## P0-4. 실제 스키마 생성 전략과 ENUM 매핑이 미확정

현재 백엔드 설정과 개발 문서는 `spring.jpa.hibernate.ddl-auto=update`로 엔티티가 테이블을 만든다고 설명한다.

반면 Claude 전달본은 다음을 전제로 한다.

1. generated SQL 적용
2. constraints SQL 적용
3. 트리거와 부분 인덱스 적용

`ddl-auto:update`만 사용하면 constraints SQL의 CHECK, 부분 유니크 인덱스, `updated_at` 트리거가 자동 적용되지 않는다. 그러면 이번 스모크 테스트에서 확인한 보호장치가 실제 개발 DB에는 없게 된다.

또한 generated SQL은 PostgreSQL 네이티브 ENUM을 만든다. JPA에서 단순히 `@Enumerated(EnumType.STRING)`만 쓰면 문자열 파라미터와 네이티브 ENUM 타입이 충돌할 수 있다.

### 권장 결정

둘 중 하나를 팀 규칙으로 고정한다.

#### 권장: SQL 마이그레이션을 스키마 원본으로 사용

- Flyway 또는 명시적 초기화 SQL 사용
- `ddl-auto=validate`
- ENUM은 초보 팀에 단순한 `varchar + CHECK` 방식 권장
- DBML은 다이어그램/설계 문서로 사용
- generated SQL을 그대로 운영 마이그레이션으로 간주하지 않음

#### 대안: Hibernate가 스키마 생성

- `ddl-auto=update` 유지
- 별도 constraints SQL을 모든 환경에 수동 적용해야 함
- 네이티브 ENUM 매핑 설정 필요
- 환경마다 제약 누락 가능성이 커서 권장하지 않음

## P1-1. `checks {}` 원인 설명은 사실과 다름

Claude 문서는 `checks {}`가 DBML 스펙에 없거나 최신 `@dbml/core`가 지원하지 않는다고 설명한다. 이는 현재 공식 문서와 맞지 않는다.

DBML 공식 문서는 컬럼 `check:`와 테이블 `checks {}`를 모두 공식 문법으로 명시한다. 2025-11 공식 릴리스 노트도 Check constraint 지원 추가를 발표했다.

- 공식 문법: https://dbml.dbdiagram.io/docs/#check-definition
- 공식 릴리스: https://docs.dbdiagram.io/release-notes/2025-11-dbml-check-constraint/

공식 Parser Playground v10.0.0에서도 `checks {}` 최소 예제를 직접 입력해 `No diagnostics`를 확인했다. `Indexes` 뒤에 `checks`를 둔 최소 예제도 통과했다.

따라서 원본 전체 파일에서 SyntaxError가 발생했다면 정확한 원인은 다음 중 하나를 추가 조사해야 한다.

- 실제 설치된 패키지/파서 경로가 보고한 버전과 달랐음
- legacy parser/API를 사용했음
- 해당 블록 주변의 다른 토큰이나 전체 파일 문맥 문제
- 실행한 명령·입력 파일이 보고서의 파일과 달랐음

CHECK를 별도 SQL로 분리한 현재 수정본 자체는 유효한 선택이다. 다만 리뷰 문서에서 “DBML 미지원 문법”이라는 단정은 “현재 사용한 로컬 파서 실행에서 실패하여 별도 SQL로 분리했다”로 수정해야 한다.

## P1-2. 문항 추출 작업 유형을 가정으로 확정하면 안 됨

`job_posting_questions.source_ai_task_id`를 `POSTING_COMPETENCY_EXTRACTION` 작업과 연결한 것은 구현 가능한 선택이지만 아직 제품 계약이 아니다.

1. 공고 원문 분석 한 번으로 역량과 문항을 함께 추출한다.

현재 화면과 팀 난이도를 고려한 권장은 1번이다. 이 경우 task type 이름을 `POSTING_ANALYSIS`로 바꾸면 실제 출력인 “역량+문항”을 더 정확하게 표현한다.

반대로 유지하려면 공고 문항/답변 API에 requirements와 addressed를 명시하고 화면에도 표시해야 한다. “나중에 쓸 수도 있음”만으로 최종 MVP ERD에 남기는 것은 권장하지 않는다.

## P1-4. 테스트 통과 범위가 리뷰 표현보다 좁음

제공 테스트는 정상적으로 통과하지만 다음은 검증하지 않는다.

### Career DB

- `posting_competencies.weight` 범위
- evidence offset 쌍의 정합성
- `job_posting_questions.sequence > 0`
- `char_count`, `byte_count` 음수 차단
- `requirement_seq > 0`
- `(user_id, job_posting_id)` 매칭 유니크
- 비활성 문항 뒤 동일 sequence 재등록
- 다른 사용자의 answer와 experience 연결 방지

### AI DB

- 네 가지 task type 각각의 필수/불필요 target 조합
- DRAFT 외 MATCH/INTAKE/EXTRACTION 부분 유니크
- FAILED/COMPLETED/RUNNING/PENDING 각 상태의 시각 조합
- 같은 idempotency key 재요청 처리 정책
- MATCH 실행 중 최신 경험 변경 시나리오

“전체 CHECK 동작 검증 완료”보다는 “선정한 주요 제약 6개씩 통과”가 정확한 표현이다.

## P2. 추가 보완 권장

### 작업 대상 CHECK를 더 엄격하게

현재 `ck_ai_task_targets`는 필요한 ID가 있는지만 검사하고, 관련 없는 ID가 같이 들어오는 것은 허용한다. 예를 들어 `EXPERIENCE_INTAKE`에 `external_question_id`와 `external_job_posting_id`가 같이 들어가도 통과한다.

혼란 방지를 위해 task type별로 불필요한 target은 NULL까지 강제할 수 있다. 다만 request_payload에 다중 대상이 필요해질 수 있으므로 AI API 계약 확정 후 적용한다.

### 멀티테넌트 소유권

DB는 사용자 A의 answer에 사용자 B의 experience를 연결하는 것을 직접 막지 않는다. API 서비스에서 반드시 소유권을 검사하고 통합 테스트로 보장해야 한다. DB까지 강제하려면 연결 테이블에 user_id를 포함한 복합 FK 설계가 필요하다.

### 테스트 반복 실행성

스모크 테스트는 새 DB의 ID가 1부터 시작한다고 가정하고 테스트 데이터를 커밋한다. CI에서 반복 실행하려면 트랜잭션 후 ROLLBACK하거나 테스트 전용 스키마를 매번 새로 만드는 규칙을 명시한다.

## Claude에게 전달할 요약

1. 생성 SQL과 제공 스모크 테스트는 독립 재현했고 모두 통과했습니다.
2. `checks {}`는 공식 DBML 문법이며 Parser Playground에서도 통과합니다. 현재 수정본의 SQL 분리 방식은 사용 가능하지만 “미지원 문법”이라는 원인 설명은 수정이 필요합니다.
3. `job_posting_questions(job_posting_id, sequence)` 전역 UNIQUE는 `is_active=false` 보존 정책과 충돌합니다. 활성 행 부분 유니크로 변경해야 합니다.
4. MATCH inflight unique는 실행 중 새 경험 변경을 누락할 수 있습니다. MATCH만 인덱스를 제거하고 결과 input_hash 검증을 하거나 rerun coalescing을 구현해야 합니다.
5. 현재 구현은 Slack 세션이고 최종 문서는 Supabase JWT입니다. 인증 방식을 먼저 확정하고, Supabase 채택 시 Career 사용자 upsert 흐름을 API에 추가해야 합니다.
6. 현재 `ddl-auto:update`와 별도 constraints SQL/네이티브 ENUM이 충돌합니다. Flyway+validate 및 varchar+CHECK를 권장합니다.
7. requirements/addressed를 실제 화면에서 쓰지 않으면 최종 MVP ERD에서 제거하는 것이 맞습니다.
